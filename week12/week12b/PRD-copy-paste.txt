PROJECT OVERVIEW

Maui Luxury Vacation Rentals Dashboard is a three-page React application that introduces visitors to Maui vacation rentals, helps travelers browse listings, and establishes the operational foundation for property management. The first page is a Marketing Page that communicates the brand promise and encourages exploration. The second page is a Visitor Dashboard that displays live property data from the existing Express and MongoDB backend. The third page is an Admin Dashboard foundation that prepares the system for future listing management workflows.

The business goal is to convert browsing interest into serious travel intent by presenting authentic Maui stays in a way that feels clear, scenic, and trustworthy. The experience should emphasize local rentals, affordability, and traveler-friendly amenities such as kitchens, parking, beach access, and long-stay comfort. The Visitor Dashboard should continue that experience by making listings easy to scan and compare.

This PRD defines why the React frontend exists and what it must deliver. The Marketing Page should establish the rental brand for first-time visitors, while the Visitor Dashboard should provide a scalable component foundation tied directly to the Week 11 backend API. The result should be a deliberate frontend structure that supports the larger Term Project without major redesign.

DATA FLOW

Property data originates in MongoDB and is exposed through the existing Express API. Each property includes fields such as name, island, type, description, amenities, targetSegment, and imageURL. The React frontend will request listings from GET /api/properties, optionally using the island filter, and store the response in state at the page-container level.

The Visitor Dashboard container passes property objects into presentational components such as PropertyGrid and PropertyCard through props. The Marketing Page may use some static copy for storytelling, but its labels and amenity language should remain aligned with the backend schema so the message reflects real inventory. Data should move in one direction: backend to stateful parent, then parent to child components.

User actions such as selecting the CTA or applying a listing filter should trigger navigation or state changes rather than direct DOM manipulation. This keeps the frontend consistent with React design principles and provides a clean foundation for future search, favorites, and admin management features.

WEEK 14C EXTENSION: AUTHENTICATION AND SECURITY

SECTION A - AUTHENTICATION REQUIREMENTS

Authentication Method
The Admin login system will use Passport.js LocalStrategy with username field configured as email plus password. The admin submits credentials through a standard HTML/React login form, and the backend validates those credentials against stored user records. The same LocalStrategy pattern used in Week 14B standalone practice will be applied to the Term Project backend for consistency and reduced integration risk.

Admin User Definition
The admin user in this application is Kai, the Maui property manager responsible for listing quality and operational accuracy. Unlike a public visitor, an authenticated admin can access protected management functions such as creating or editing listing descriptions, updating amenities, toggling featured status, and reviewing internal dashboard controls. Public users can browse listings and view marketing content but cannot access or modify any admin-only data.

Protected Routes
At minimum, the following routes are protected and must require authentication:
- /admin/login (public route for credential submission)
- /admin/dashboard (protected route for admin tools and operational metrics)

Additional admin routes may be added later, such as /admin/properties/new and /admin/properties/:id/edit, but those are out of current scope.

Login Flow (Plain English)
1. The admin navigates to /admin/login and enters email and password.
2. The browser submits the form to the backend login endpoint.
3. Passport LocalStrategy receives the credentials and looks up the user by email.
4. The submitted password is compared against the stored bcrypt hash.
5. If credentials are valid, Passport serializes the user ID into the session.
6. The server redirects the admin to /admin/dashboard.
7. If credentials are invalid, the server redirects back to /admin/login with an error message.

Session Management
Authentication will use server-side sessions through express-session. Target session duration is 60 minutes of inactivity for this class project baseline. If the admin closes the browser, the session cookie should be treated as expired at browser end unless explicitly configured otherwise. If a valid session exists, protected route access continues; if the session has expired or is missing, the user is redirected to /admin/login.

SECTION B - SECURITY REQUIREMENTS

Password Hashing Policy
All passwords must be hashed with bcrypt using 10 or more salt rounds (project target: 12). Plain-text password storage is unacceptable because any database leak would immediately expose reusable credentials, creating high-risk account takeover scenarios across other sites where users may reuse passwords.

Environment Variable Management
Sensitive values must be stored in .env and never hardcoded in source files. Required secret/config entries include:
- SESSION_SECRET
- MONGODB_URI
- VITE_WEATHER_KEY (frontend weather API key)
- Any future OAuth/API provider keys

The .gitignore file must include .env and related local secret files so secrets are not committed to GitHub.

Failed Login Handling
If login fails, the server should not reveal whether the email or password was incorrect. The application redirects to /admin/login with a generic error message such as "Invalid credentials." Failed attempts should be logged server-side for basic monitoring. In future hardening, rate-limiting and account lockout thresholds can be added.

Additional Security Risk and Mitigation
Risk: Cross-site scripting (XSS) in public review or description fields, where malicious input could inject script into property pages.
Mitigation: Validate and sanitize all user input server-side before storage, escape rendered output in templates/components, and avoid direct HTML injection patterns. Apply a strict content-security policy in production if available.
